# Repository instructions

Read the relevant skill and its references before editing. Keep agent instructions and canonical technical references in English. Human README guides have English, Chinese, Japanese, French and German versions as requested; demonstrations use their declared languages.

- `bilingual-translation` owns the source-first translation workflow and optional semantic exchange contract; renderers consume it through explicitly discovered installed skills. `bilingual-html` owns its independent HTML layout schema, renderer and presentation assets. Supplied pairs render without a translation dependency.
- Maintain one owner per implementation. `skills/bilingual-pdf` owns the renderer, templates, LaTeX package, reusable article assets and layout references. `study-notes` owns only its teaching workflow, native learning components and learning example; it requires the installed bilingual skill rather than carrying distribution copies.
- Test clean installations without source-checkout access: bilingual-pdf alone, and the study skill with its explicitly installed bilingual dependency at a separately discovered path. Never hardcode a sibling installation, automatically download a dependency or call repository maintainer tools from an installed skill.
- Preserve original user inputs. Do not overwrite or silently change supplied translations.
- Keep private source material, account data, operational reports, credentials and machine-specific paths out of published files and history.
- Use original examples and retain dependency licenses. A public repository is not automatically freely reusable.
- Read source text and inspect actual PDF pixels. Compiler success and rules cannot substitute for semantic, factual or language review.
- Report passes, failures and unrun checks separately. Never claim all languages or accessibility conformance based on a small sample matrix.
- Run schema/security tests, package ownership checks, applicable render/visual tests, clean installation and privacy checks before publication. Keep generated review evidence in a private build directory; publish only sanitized test summaries and authorized examples.
- Do not weaken a validation gate merely to make a test pass. Fix the canonical code and rerun affected outputs.

## Curated example artifacts

Track curated PDFs and previews beside their sources under `skills/bilingual-pdf/examples/<language-pair>/` and `skills/study-notes/examples/`. Keep selected study forms flat as `notes.pdf`, `quick-reference.pdf`, `keyword-index.pdf` and `decision-tree.pdf`. Regenerate them with `tests/README.md`, inspect content and metadata, and refresh each skill's local `examples/MANIFEST.json`. Never duplicate installed examples in a root examples directory. All article pairs must translate the same complete source and exercise the same features; recurring languages must remain text-identical. Keep compact compatibility fixtures in `tests/fixtures/`. Transient builds, logs, private inputs and full matrices stay ignored; do not substitute Actions artifacts for these directly browsable examples.

For bilingual-pdf articles, keep native LaTeX and structured content as equal entry routes through the one canonical package. Study-notes notes, quick references and indexes remain native LaTeX. Decision graphs may use the owned, versioned structured-graph importer as their sole content/edge source; it emits existing native semantic components. Provenance JSON is not a manuscript adapter. After editing article fixtures, run tools/export_native_examples.py; native example projects remain directly editable and buildable without Python. Keep source records and rendered outputs inside the owning skill, with shared example illustrations stored once in bilingual-pdf/examples/shared and paralleltext.sty stored once in bilingual-pdf/assets. A portable delivery may stage the required assets, but installed examples must not become duplicate renderers. Test actual agent authoring from raw sources as well as compilation.

Keep defaults usable without setup. New visual behavior belongs in the canonical package's documented native configuration or standard package hooks, never in per-example hardcoded variants. Test meaningful sparse overrides, invalid inputs, both print parities and native/structured equivalence. Use skill-level references and licenses; do not add repeated per-example README/license files. Language-pair folders are useful project boundaries, while the single learning set stays directly under examples/.

## Documentation ownership

Every skill, including a new one, must ship its own LICENSE and human README.md, README.zh-CN.md, README.ja.md, README.fr.md and README.de.md. Root catalog entries must link the matching human guide, never fall back to SKILL.md. Keep guides brief and link owned references/examples rather than duplicating them. Repository-specific requirements take precedence over generic skill-authoring minimalism. Before delivery, check the changed files against these requirements and distinguish structural test evidence from human content/language review.

Keep the root README a concise catalog with install/dependency guidance. Each skill README is its human use/example guide; each SKILL.md is a concise agent workflow. Keep full rendering, language, configuration and safety references only in bilingual-pdf. Resolve cross-skill references through the host's installed-skill discovery, not relative sibling links. Use complete worked examples plus a minimal native reference snippet instead of maintaining parallel starter trees. Preserve native/structured parity, full configuration detail, RTL/CJK requirements and flowing-prose behavior when simplifying documentation.

## Positive-first skill guidance

Teach the correct procedure first. When a cold-context agent fails, diagnose missing or unclear steps, inputs, expected outputs and applicable context; repair that explanation with concrete examples a fresh agent can follow. Add a negative rule only for a sufficiently general error or risk, with its rationale and scope stated, alongside the correct alternative. Retest the intended behavior and remove ineffective fixes, including restrictions that merely redirect the error. Use the [cold-context validation workflow](tests/README.md#cold-context-skill-validation) for this review.

## Automated verification and co-maintenance

Follow [testing-workflow](skills/testing-workflow/SKILL.md) and its cost/performance reference. These principles are mandatory:

- Use the project's native test/benchmark framework and language. Let code execute cases, assert outcomes and aggregate failures in one invocation or a small number of resource-bounded batches; do not substitute per-case tool calls, manual scoring or one subagent per test.
- Maintain tests, regressions, benchmarks, safe fixtures and dependencies beside the implementation in the same change. Review assertion validity; reproduce a bug before repair when practical and preserve meaningful public-contract coverage rather than production-logic copies or brittle internals.
- Start with affected checks after the final relevant edit. Broaden for concrete integration risks or required release gates; consider setup, execution, diagnosis, maintenance, resource and tool-call cost. Preserve required checks and user exclusions. Stop at sufficient evidence, remove obsolete redundancy and fill real gaps rather than inventing coverage targets or repeated full-suite gates.
- Use documented clean-checkout commands and shared local/CI entry points. Isolate state, automate setup/teardown and process cleanup, bound workers/time/resources, and separate fast checks from explicit expensive/network/real-model profiles. Record relevant versions, seeds and fixture/model hashes.
- Preserve failure exit status and evidence. Distinguish passed, failed, skipped, blocked, incomplete and unrun work; missing dependencies, zero collected tests or truncated reports are not a pass. Diagnose flakiness instead of retrying until green. Identify the tested source/output state.
- Benchmark against a comparable baseline with defined workload, boundaries and environment. Use native calibration; routine Go work starts with `go test -bench '<affected-pattern>' -count=1` per source version. Do not invent fixed repetition budgets or statistical thresholds. Preserve raw results, investigate anomalies and repeat affected measurements only for a stated uncertainty question; suite elapsed time and noisy shared-machine timings alone are not reliable performance gates.
- Keep factual, language, semantic and visual review explicit where automation cannot establish correctness. Convert reproducible manual findings into regressions when feasible. Never publish private fixtures, credentials or machine-specific logs, or treat automated execution as extra permission for external services, paid work, deployment or excluded evaluations.
